## Why

The web companion auth/registration logic has zero test coverage and, as currently structured, cannot get any: the credential-verification code lives inline in `sdf_ble_companion_auth_access()` (`firmware/components/sdf_ble_companion/src/sdf_ble_companion.c`), whose component unconditionally `REQUIRES bt esp_wifi esp_netif esp_http_client` and therefore cannot build for `IDF_TARGET=linux`; and the registration-approval glue (`sdf_ble_companion_on_auth_request`, `sdf_app_on_web_reg_auth_result`, `sdf_app_on_admin_action_complete` in `firmware/components/sdf_app/src/sdf_app.c`) lives in `sdf_app`, which unconditionally `REQUIRES sdf_ble_companion`. `sdf_app`'s `CMakeLists.txt` even has a dangling `if(IDF_TARGET STREQUAL "linux") # We still want to compile sdf_app on Linux for unit tests instead of excluding it. endif()` block with no body — evidence of a prior, abandoned attempt at exactly this.

This is not a minor gap: the code being untested is the actual security boundary — constant-time password hash comparison (`mbedtls_ct_memcmp`), `LOGIN`/`REGISTER` command handling, and a physical-fingerprint admin-approval gate that decides whether a new web user gets persisted at all. `sdf_app_on_admin_action_complete` carries a comment warning that if its timeout/reject path breaks, web registration gets "permanently" stuck pending — exactly the kind of behavior a regression test should be pinning down, and currently can't be.

`openspec/changes/archive/2026-08-05-fix-test-runner-build/design.md` already named this gap as an Open Question and proposed a follow-up under this same name (`add-linux-target-sdf-app-support`), but scoped it as "making `sdf_app`/lock-flow linux-testable" broadly — which that same design doc's Non-Goals section explicitly rejected as "real architectural changes to production code... regression risk out of proportion to scope." Investigating further shows that framing was too broad: the auth logic's actual dependencies (`mbedtls`, `sdf_storage`, `sdf_event_router`, `sdf_services`'s `web_reg_auth` state) are all already linux-clean and already tested elsewhere in this codebase. Only the GATT wire handling (`os_mbuf`, NimBLE types) is genuinely hardware/stack-bound. So the fix doesn't require making `sdf_app` or `sdf_ble_companion` linux-buildable at all — it requires extracting the *decision* logic out of both.

That decision logic already has a documented home: `openspec/specs/sdf-services-tasks/spec.md`'s "Requirement: Web Registration Authorization" states `sdf_admin_task`/`sdf_services` SHALL own the admin-auth-gates-registration workflow, with the GATT server only executing the result ("GATT server saves credentials to NVS," "GATT server marks connection authenticated"). The implementation only partially matches that spec today: `sdf_services_admin.c` already owns the admin-approval state machine (`SDF_SERVICES_ADMIN_ACTION_WEB_REG_AUTH`) and `sdf_services.c` already owns the pending-auth state (`web_reg_auth_pending`, `request_web_username`, `sdf_services_set/get_web_reg_auth`). What leaked out to the wrong place is only the hash-comparison decision (inline in `sdf_ble_companion.c`) and the "what to persist" decision (inline in `sdf_app.c`). Both `sdf_ble_companion` and `sdf_app` already `REQUIRES sdf_services`, and `sdf_services` already `REQUIRES sdf_storage` — so moving the decision logic into `sdf_services` closes the gap with zero new component-graph edges. A new standalone component was considered and rejected: it would require the same new `REQUIRES` edges from both call sites anyway, without the benefit of already-aligned spec intent, already-owned adjacent state, or an already-wired, already-linux-tested test target (`test_sdf_services.c`) to extend. (`sdf_state_machines` was also considered and rejected — it's tightly coupled to `fingerprint.h`/`sdf_drivers` biometric types; folding unrelated web-auth logic in there would be a domain mismatch.)

## What Changes

- Add `firmware/components/sdf_services/src/sdf_services_web_auth.c`, matching the component's existing per-responsibility file split (`_match.c`, `_enroll.c`, `_admin.c`, `_button.c`), containing pure decision functions extracted from the two call sites currently holding them:
  - Login verification: given a looked-up `sdf_storage_web_user_t` and a submitted password hash, decide authenticated/rejected (wraps `mbedtls_ct_memcmp`, currently inline in `sdf_ble_companion_auth_access()`).
  - Registration outcome: given an admin-action result (authorized/denied/timeout), decide what to persist (mirrors `sdf_app_on_web_reg_auth_result`'s logic minus the actual `sdf_storage_web_user_save()` call) and what auth reply to send.
  - Pending-state unlatch: the timeout/reject path currently in `sdf_app_on_admin_action_complete`, decided as pure logic so its "must always resolve the pending BLE client" guarantee is directly testable.
- Add `PRIV_REQUIRES mbedtls` to `sdf_services`'s `CMakeLists.txt` (its only new dependency — `sdf_storage` is already required).
- `sdf_ble_companion_auth_access()` calls the new `sdf_services` function for the login decision instead of inlining the hash compare (no new `REQUIRES` — `sdf_ble_companion` already requires `sdf_services`).
- `sdf_app.c`'s three callback functions call the new `sdf_services` functions for the decision, then perform the I/O (`sdf_storage_web_user_save`, `sdf_ble_companion_reply_auth`) based on the returned result (no new `REQUIRES` — `sdf_app` already requires `sdf_services`).
- Extend `firmware/components/sdf_services/test/test_sdf_services.c` (already wired into `test_runner`) covering: valid/invalid login hash comparison (including that the constant-time property isn't accidentally short-circuited), register-authorized → correct user/permission decided, register-denied → no user decided, admin-action timeout/reject → pending state always resolves (regression test for the documented "permanently block" risk).
- **No changes** to `sdf_app`'s or `sdf_ble_companion`'s `REQUIRES`, and no new component or `test_runner` component-dir wiring needed — both remain hardware/stack-bound and out of `test_runner`'s linux build graph, exactly as `fix-test-runner-build`'s design doc intended. This change is explicitly narrower than what that design doc's Open Question implied.

## Capabilities

### New Capabilities
(none)

### Modified Capabilities
- `sdf-services-tasks`: its existing "Web Registration Authorization" requirement already describes this workflow at the spec level (admin-auth gates registration, GATT server executes the result); this change adds scenario-level detail for the decision guarantees now backed by tests — constant-time login hash comparison, and that the timeout/reject path always resolves the pending request (never leaves it permanently stuck). No change to `ble-companion-service`'s GATT-level requirements — external behavior is unchanged, this is an internal refactor plus net-new coverage.

## Impact

- New file: `firmware/components/sdf_services/src/sdf_services_web_auth.c` (plus a matching header addition, likely `sdf_services_internal.h` or a new `sdf_services.h` entry for the login-verify function that `sdf_ble_companion` calls publicly).
- `firmware/components/sdf_services/CMakeLists.txt` (`PRIV_REQUIRES mbedtls`).
- `firmware/components/sdf_ble_companion/src/sdf_ble_companion.c` (delegates login decision to `sdf_services`).
- `firmware/components/sdf_app/src/sdf_app.c` (delegates registration/timeout decisions to `sdf_services`).
- `firmware/components/sdf_services/test/test_sdf_services.c` (extended — already wired into `test_runner`, no new `EXTRA_COMPONENT_DIRS`/`COMPONENTS`/`test_runner_main.c` wiring needed beyond new `RUN_TEST()` entries).
- No new `openspec/specs/firmware-host-test-runner/spec.md` entry needed — `sdf_services` is already listed under "Wired-In Component Coverage."
- Resolves the Open Question left by `openspec/changes/archive/2026-08-05-fix-test-runner-build/design.md`, with narrower scope than that doc's original framing, and completes the architecture `openspec/specs/sdf-services-tasks/spec.md`'s "Web Registration Authorization" requirement already describes.
- Independent of `add-linux-host-tests-config-platform` and `spike-sdf-ota-linux-target` — no ordering dependency, though it's the highest-value of the three given what's currently untested.

## Why

`sdf_button_task`, `sdf_enroll_task`, and `sdf_admin_task` each wake on a fixed ~100ms cadence forever, `sdf_power_task` polls its sleep decision every 250ms even while just waiting out a timer, and the enrollment button's `iot_button` driver runs its own internal scan timer every ~20ms with no idle self-stop. `CONFIG_PM_ENABLE=y` and `CONFIG_FREERTOS_USE_TICKLESS_IDLE=y` are both set, so FreeRTOS's automatic opportunistic light sleep only gets a window as long as the shortest wake cadence among all runnable tasks — these five periodic wakeups keep that window pinned near 20-100ms, preventing meaningful light-sleep residency on a battery device between `sdf_power_task`'s own deliberate, already-correct `esp_light_sleep_start()` windows. `openspec/specs/sdf-services-tasks/spec.md` already documents `sdf_button_task` and `sdf_enroll_task` as event-driven/ISR-driven with no polling — the implementation has drifted from that contract.

`sdf_admin_task` is included because it is the **binding constraint**: with it left polling at 100ms, fixing the other tasks reduces how much CPU burns inside each window but not the number of wake events, so the tickless window stays pinned at 100ms and the change does not deliver its own stated outcome. Unlike the others its poll is not vestigial — it services a real 10-second pending-admin-action timeout (`sdf_services_admin.c:173-194`) — but it services it at 100ms granularity, 100x finer than the deadline requires.

## What Changes

- **`sdf_button_task`: removed entirely** — **BREAKING** (internal only; no public API signature changes). The task's loop does no work: press detection and dispatch already happen entirely inside `iot_button`'s own `esp_timer` scan callback, which invokes `sdf_button_cb`/`sdf_button_single_click_cb` directly. Everything else in the task is dead: `sdf_button_isr` is defined but never registered, the `suspended` flag is written on `POWER_WAKE`/`POWER_SLEEP` but never read, and `sdf_button_task_emit_button_press()`/`sdf_button_task_emit_admin_action_request()` are defined but never called. Its only live responsibilities are one-time `iot_button` setup/teardown, which become plain `sdf_button_init()`/`sdf_button_deinit()` functions called from `sdf_services_start_tasks()`/`sdf_services_stop_tasks()` (preserving today's start/stop symmetry). This drops a task, its 3 KB stack, its 10-deep event queue, and its two event-router subscriptions. `sdf_button_dispatch_action()` and the single-click resolution logic are unchanged and stay exactly where they are.
- Flip `button_gpio_config_t.enable_power_save` to `true` for the enrollment button so `iot_button`'s internal ~20ms scan timer self-stops when idle (`debounce_cnt == 0`, no press in progress) and resumes on the next GPIO interrupt, instead of running forever regardless of `sdf_button_task`.
- **`sdf_enroll_task`**: idle regime (state machine inactive, the common case) blocks on its event queue with a WDT-safe timeout cap, bounded well under the 5s task-WDT timeout, instead of the current `xQueueReceive(100ms)` + unconditional `vTaskDelay(100ms)`. Active-enrollment regime (`sdf_enrollment_sm_is_active()`) drives step retries via an `esp_timer` one-shot re-armed on each `SDF_ENROLL_ACT_RETRY_STEP`, instead of an unconditional poll running regardless of state. The 10ms boot-readiness busy-wait (`while (!sdf_services_is_ready())`) becomes notify/event driven. `sdf_services_stop_tasks()` pushes a stop signal into this task's queue instead of relying on poll cadence to observe `stop_requested`.
- **`sdf_admin_task`**: replace the fixed `xQueueReceive(100ms)` loop wait with a deadline-computed wait — block until the pending admin action's 10-second expiry when one is pending, and block for the WDT-safe cap when none is. Because `pending_admin_action` is also set directly by callers that emit no event (`sdf_services_request_admin_action()`, and the button dispatch path), setting a pending action additionally notifies this task so its timeout countdown starts promptly rather than at the next cap expiry. `sdf_services_stop_tasks()` pushes the same stop signal into this task's queue as into `sdf_enroll_task`'s.
- **`sdf_power_task`**: replace the fixed 250ms `STAY_AWAKE` loop delay with a wait computed from the nearest real deadline (idle-before-sleep remaining, post-wake-guard remaining, next-battery-report remaining), capped at a WDT-safe max. `sdf_power_mark_activity()` additionally notifies the task so it can recompute its wait immediately rather than sleeping through activity that occurred right after it last checked. The deliberate `esp_light_sleep_start()` call and checkin-interval sleep path are unchanged — this only targets the `STAY_AWAKE`/poll spells.
- Update `doc/rtos_tasks.md`: drop `sdf_button` from the task table and delete its §2.6 section (replacing it with a note that button handling is taskless), correct the `sdf_power` / `sdf_enroll` / `sdf_admin` trigger, loop-interval, and watchdog rows, and fix a pre-existing drift found while scoping this — the §5 watchdog table claims `sdf_admin` has a 15s task watchdog, but `sdf_services_admin.c` includes `esp_task_wdt.h` and never calls `esp_task_wdt_add(NULL)`, so that task is not watchdog-registered at all.

## Capabilities

### New Capabilities
- `sdf-power-task`: `sdf_power_task`'s `STAY_AWAKE` wait behavior — deadline-computed delay, WDT-safe cap, activity-notification-driven early wake. `sdf_power` currently has no capability spec under `openspec/specs/`.

### Modified Capabilities
- `sdf-services-tasks`: button handling no longer runs as a task at all (removing the button task's idle-loop, event subscriptions, and shutdown-protocol participation); `sdf_enroll_task`'s and `sdf_admin_task`'s idle-loop behavior (event-driven blocking waits with a WDT-safe cap, deadline-computed wait for the pending-action timeout, `esp_timer`-driven enrollment-step retries, push-driven stop signal instead of polled `stop_requested`); the enrollment button's `iot_button` power-save configuration; and the removal of implementation-name coupling to `sdf_button_task` in one remaining button-behavior requirement.

## Impact

- Code: `firmware/components/sdf_services/src/sdf_services_button.c` (task removed, reduced to init/deinit + the retained dispatch logic), `sdf_services_enroll.c`, `sdf_services_admin.c` (deadline-computed wait, pushed stop signal), `sdf_services.c` (`sdf_services_start_tasks`/`sdf_services_stop_tasks`, now managing 3 tasks; pending-action-set notifies the admin task), `sdf_services_internal.h` (drop `sdf_button_task` declaration and `button_task` handle), `firmware/components/sdf_power/src/sdf_power.c`.
- Docs: `doc/rtos_tasks.md` (button task section removed; trigger/loop-interval/watchdog rows for the other two tasks).
- No public API signature changes: `sdf_services_start_tasks()`/`sdf_services_stop_tasks()` keep their signatures and contracts, and `sdf_button_dispatch_action()` — the only button symbol the tests touch — is unchanged. `sdf_power_mark_activity()` gains an internal task-notify side effect but its contract is unchanged.
- Frees a task slot, 3 KB of task stack, a 10-entry event queue, and two event-router subscriptions.
- **Behavior change**: the pending-admin-action timeout is still 10 seconds, but is now detected within the WDT-safe cap of its true expiry rather than within 100ms of it. Nothing in the system depends on sub-second timeout precision, but it is a real loosening and is specified explicitly.
- **Sequencing**: this change lands **fourth**, after `unify-pending-admin-action-led-mapping`, `centralize-unclaimed-device-bootstrap`, and `dispatch-admin-actions-off-esp-timer`. By then `sdf_button_task` is unambiguously vestigial — `dispatch-admin-actions-off-esp-timer` has already moved button dispatch to `sdf_admin_task` — so removing it is deletion with no behavioral surface. **At archive time**, three of this change's MODIFIED requirement blocks are expected to be droppable rather than reconciled: `centralize-unclaimed-device-bootstrap` will already have reworded "Simplified Pre-Enrollment Bootstrap Branch", and `dispatch-admin-actions-off-esp-timer` will already have reworded "State-Dependent Single-Click Setup Action" and "Double-Press Requests BLE Companion Pairing Window". Only "Admin-Only Actions Not Bound To Physical Button Gestures" still needs this change's rewording. Verify against the live spec before archiving rather than assuming.
- Out of scope: `sdf_match_task`'s own 400ms poll (not part of this request; it is no longer the binding constraint once `sdf_admin_task` is fixed, but it does become the next one) and pre-existing, unrelated drift elsewhere in `doc/rtos_tasks.md` (e.g. the button press-mapping table, admin timeout values).
